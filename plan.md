# План: ограниченное окно аудиокэша в cache-режиме

## Статус

Реализовано. Проверки: `npm run check`, `npm run build`, Docker smoke в `cache`-режиме (`/api/health`, `audioDeliveryMode=cache`).

## Решение

- В `cache`-режиме держать в памяти текущий трек и настраиваемое количество будущих треков.
- Новый параметр: `AUDIO_CACHE_LOOKAHEAD=2` — количество будущих треков сверх текущего.
- Текущий трек не удалять в момент `round_started`:
  - браузер может ещё запрашивать `/api/audio/:id` и range-запросы;
  - удаление сразу после старта может дать 404 и оборвать воспроизведение.
- Освобождать текущий трек после `revealRound`, когда экран результата уже не использует аудио.
- После старта раунда запускать фоновую догрузку следующего трека.
- `AUDIO_CACHE_LOOKAHEAD` действует только в `cache`-режиме. В `direct`-режиме поведение не меняется.
- Клиент не меняем.

## Почему это нужно

Сейчас `start_game` кэширует весь игровой пул:

- `server/index.ts:197-205` кэширует все `pool.playableTracks`;
- размер пула задаётся в `server/roundPlanning.ts:30-39`;
- для 5 раундов это около 25 треков, для 20 — около 40, для длинных игр — до 76;
- `server/audioCache.ts:31-69` скачивает и хранит полный файл, а не только короткий фрагмент;
- лимит `AUDIO_CACHE_MAX_BYTES` действует на один файл, а не на весь кэш.

Итог: память растёт от размера всего пула. Новая схема ограничивает её несколькими треками.

## Целевая схема

### Данные комнаты

Добавить отдельные структуры:

- `roomTracks` — метаданные всего пула, без обязательного аудио в памяти;
- `roomAudioWindow` — треки, для которых уже есть локальный `/api/audio/:id`;
- `roomAudioCursor` — позиция в пуле метаданных;
- `roomAudioCurrent` — текущий трек, чтобы освободить его после reveal.

`roomTracks` в cache-режиме хранит upstream-URL, а локальные URL находятся только в `roomAudioWindow` и в текущем вопросе.

### Старт игры

1. Подготовить метаданные пула через `prepareTrackPool()`.
2. Перемешать пул и сохранить в `roomTracks`.
3. Сбросить окно, курсор и текущий трек.
4. Закэшировать только `AUDIO_CACHE_LOOKAHEAD + 1` треков: текущий + будущие.
5. Запустить первый раунд.

### Старт раунда

1. Убедиться, что окно заполнено до `AUDIO_CACHE_LOOKAHEAD + 1`.
2. Передать `GameEngine` список кандидатов из окна.
3. Дать движку выбрать текущий трек только из этого списка.
4. Удалить выбранный трек из окна.
5. Отправить `round_started`.
6. Запустить фоновую догрузку ещё одного трека.

Так при `AUDIO_CACHE_LOOKAHEAD=2` в момент старта раунда в окне 3 трека: текущий + 2 будущих. После выбора текущего остаётся 2 будущих, затем фоновая догрузка возвращает окно к 3 трекам.

### Во время раунда

- Текущий трек остаётся в `AudioCache` до reveal.
- После старта раунда в фоне догружается следующий трек.
- Пиковая память: текущий + 3 будущих = 4 трека при значении по умолчанию.
- Новый трек получает примерно длительность вопроса + паузу результата, то есть около 20 секунд при настройках по умолчанию.

### Reveal

В колбэке `revealRound()`:

1. Освободить текущий трек через новый метод `AudioCache.removeByUrl()`.
2. Удалить его из `roomAudioWindow`, если он там ещё есть.
3. Не удалять трек, если тот же локальный URL используется другим треком окна.
4. Если игра не завершена, догрузить следующий трек в фоне.
5. Если игра завершена, очистить окно и кэш комнаты.

Экран результата не содержит `<audio>`, поэтому после reveal текущий трек уже не нужен.

### Длинные игры и фоновая гидратация

`hydrateRoomTrackPool()` сейчас кэширует весь фоновый пул. Это нужно изменить:

- фоновый пул добавляет только метаданные;
- новые треки добавляются в конец `roomTracks`;
- не перемешивать уже использованную часть массива, чтобы не сломать курсор;
- при необходимости пополнить `roomAudioWindow`, но не кэшировать весь пул.

### Очистка

Очищать окно, курсор и текущий трек:

- при `resetRoomToLobby`;
- при удалении комнаты через `leave_room`;
- при `reset_display_game`;
- при завершении игры;
- при повторном `start_game` из lobby/round-result.

`audioCache.clearRoom()` уже вызывается в этих сценариях; новые map’ы нужно очищать рядом с ним.

- `README.md`;

Описание: количество будущих треков, которые держатся в памяти сверх текущего. `0` означает, что после старта будет догружаться только следующий трек.

## Расчёт памяти

Пиковая память на комнату:

```text
(AUDIO_CACHE_LOOKAHEAD + 2) × AUDIO_CACHE_MAX_BYTES
```

При значениях по умолчанию:

```text
(2 + 2) × 8 МБ = 32 МБ
```

Это верхняя оценка при максимальном размере файла. Для коротких preview память будет значительно ниже.

После reveal в памяти остаётся `AUDIO_CACHE_LOOKAHEAD + 1` трек: следующий текущий и будущие.

Несколько активных комнат умножают эту оценку на их количество. Метаданные пула и вариантов ответа занимают килобайты и на общую картину почти не влияют.

## Критерии готовности

- В cache-режиме при старте игры кэшируется только стартовое окно, а не весь пул.
- Текущий трек остаётся доступен до reveal.
- После reveal текущий трек освобождается, окно пополняется в фоне.
- В памяти одновременно не больше `AUDIO_CACHE_LOOKAHEAD + 2` аудиотреков на комнату.
- В direct-режиме поведение не изменилось.
- Новые параметры и ограничения описаны в README и AGENTS.md.
- Все проверки и Docker smoke проходят.

## Риски

- Если prefetch не успел, следующий раунд может начаться с задержкой; нужно попытаться догрузить трек синхронно перед стартом.
- Если браузер повторно запросит аудио после reveal, сервер вернёт 404; по текущему UI это не требуется.
- Курсор и фоновое пополнение нужно защитить от гонок, чтобы не добавить один трек дважды.
- При `AUDIO_CACHE_LOOKAHEAD=0` запас отсутствует: следующий трек будет готов только после старта текущего раунда.
- Лимит `AUDIO_CACHE_MAX_BYTES` остаётся лимитом на файл; общий объём ограничивается именно размером окна.

# Дополнение: обрезка аудио в cache-режиме до длительности вопроса

## Статус

Реализовано вместе с оконной схемой. Проверки: `npm run check`, `npm run build`, Docker smoke в `cache`-режиме.

## Принятые решения

- Источник аудио должен быть MP3. Не-MP3 (например, demo-треки iTunes `.m4a`) в `cache`-режиме пропускается: `prepareTrackAudio` логирует ошибку и берёт следующий кандидат.
- Длительность клипа = `room.settings.questionDurationMs`, но не более 30 секунд. Значение по умолчанию — 10 секунд (`server/game.ts:104`). Ограничения: easy — 15 секунд, hard — 30 секунд (`server/game.ts:1947-1949`), сервер уже клампит настройку (`server/game.ts:228`, `1935-1939`), клиент ограничивает ввод (`src/main.tsx:2282-2284`, `979-987`).
- Клиент не меняем: `/api/audio/:id` продолжает отдавать MP3 и поддерживать Range.
- Перекодирование не используется: MP3 обрезается по границам кадров.

## Почему это нужно

Сейчас `cacheTrackAudio()` всегда скачивает upstream-файл целиком в память: `fetch()` идёт без `Range`, тело читается через `arrayBuffer()` (`server/audioCache.ts:41-50`). Проверка `AUDIO_CACHE_MAX_BYTES` выполняется только после полной загрузки (`server/audioCache.ts:50-56`). Поэтому даже при оконной схеме каждый трек в окне занимает полный размер файла, а файлы сверх лимита успевают полностью попасть в память до отказа.

Дополнительно полные песни могут появляться в режиме `hard` (`server/music.ts:629-634`) и при `YANDEX_MUSIC_ALLOW_FULL_TRACK_FALLBACK=true` (`server/music.ts:642-653`, `678`).

## 1. Новый модуль `server/mp3Clip.ts`

Добавить чистый модуль без внешних зависимостей.

```ts
export const MAX_MP3_CLIP_MS = 30_000;

export type Mp3Clip = {
  body: Buffer;
  durationMs: number;
  receivedBytes: number;
  truncated: boolean;
};

export function clipMp3Buffer(input: Buffer, targetMs: number, maxBytes: number): Mp3Clip;

export async function downloadMp3Clip(
  fetcher: typeof fetch,
  url: string,
  options: { targetMs: number; maxBytes: number }
): Promise<Mp3Clip>;
```

### `downloadMp3Clip()`

1. Выполнить `GET` с заголовками:
   - `Accept: audio/mpeg, audio/*;q=0.9, */*;q=0.8`;
   - `Range: bytes=0-` — чтобы сервер, поддерживающий Range, мог отдать 206 и не считать это полной загрузкой.
2. Если ответ не 200/206 — ошибка. На 416 попробовать повторный запрос без `Range`.
3. Если `response.body` отсутствует или сервер/прокси уже отдал всё тело целиком — скачать через `arrayBuffer()`, затем обрезать буфер. Это сценарий «скачать обязательно, лишнее отбросить».
4. Если body есть — читать поток через `reader.read()` и передавать чанки в парсер кадров.
5. Как только парсер набрал целевую длительность:
   - вызвать `await reader.cancel()`;
   - вызвать `controller.abort()`, чтобы закрыть соединение;
   - не считать отмену ошибкой, если клип уже собран.
6. Если поток закончился раньше целевой длительности — вернуть все полные кадры, которые есть.
7. Превышение `maxBytes` до достижения целевой длительности — отменить загрузку и выбросить ошибку `Audio file is too large`.
8. Если в первых ~64 КБ после ID3-тега нет валидного MP3-кадра — отменить загрузку и выбросить `Unsupported audio format: expected mp3`. Это не даёт скачивать не-MP3 целиком.

Дополнительно:

- AbortController нужен, чтобы отмена реально закрывала сокет, а не только переставала читать поток.
- Если upstream игнорирует `Range`, это не страшно: парсер всё равно остановит чтение после нужной длительности.
- Если upstream буферизует ответ целиком, отмена не поможет — тогда работает fallback с обрезкой уже полученного буфера.

### `clipMp3Buffer()`

Используется для fallback-пути и для тестов. Должен:

- пропускать ID3v2-тег в начале (syncsafe size, флаг footer);
- находить первый валидный MPEG-кадр;
- отбрасывать Xing/Info/VBRI-кадр, если он стоит первым, чтобы в файле не осталось неверной общей длительности;
- идти по кадрам до накопления `targetMs`;
- возвращать только целые кадры;
- не включать ID3v1 и хвостовой мусор;
- при отсутствии валидных кадров выбрасывать ошибку.

Парсер должен поддерживать MPEG-1/2/2.5, Layer I–III, но приоритет — Layer III. Для каждого кадра считать:

- bitrate;
- sample rate;
- padding;
- samples per frame;
- длину кадра;
- длительность кадра.

Обрезка всегда по границе кадра. Итоговая длительность может отличаться от целевой на один кадр (примерно 26 мс для 44.1 кГц Layer III), это допустимо.

Защитные ограничения парсера:

- отклонять free-bitrate (`bitrate index = 0`);
- отклонять некорректные version/layer/sample rate;
- ограничить длину кадра разумным максимумом, например 8192 байта;
- не хранить ID3-тег в результате;
- не хранить уже обработанные кадры повторно.

## 2. `server/audioCache.ts`

### Сигнатура

Расширить метод:

```ts
cacheTrackAudio(
  roomCode: string,
  upstreamUrl: string,
  options?: { maxDurationMs?: number }
): Promise<string>
```

`maxDurationMs` по умолчанию `10_000`, затем клампится в диапазон `1_000..MAX_MP3_CLIP_MS`.

### Загрузка

Заменить текущий `fetch` + `arrayBuffer()` (`server/audioCache.ts:41-56`) на `downloadMp3Clip()`.

- `mimeType` всегда `audio/mpeg`.
- `body` — обрезанный MP3.
- Проверка `body.length > maxBytes` остаётся защитной, но теперь выполняется уже после обрезки.
- Не-MP3 и слишком большие клипы не попадают в `entries`.

### Дедупликация и длительность

Сейчас ключ дедупликации — только `room + upstreamUrl` (`server/audioCache.ts:119-121`). Этого недостаточно, если комната когда-либо запросит более длинный клип.

Вариант:

- хранить в `AudioCacheEntry` поле `clipDurationMs`;
- если существующая запись покрывает запрошенную длительность — переиспользовать её;
- если существующая короче — удалить её и закэшировать заново;
- при удалении чистить `entries`, `idsByUpstreamUrl`, `idsByRoom`.

Для этого добавить внутренний `deleteEntry(id)` и, желательно, публичные `remove(id)` / `removeByUrl(url)` — они также понадобятся плану по оконной схеме.

Дополнительно добавить in-flight-дедупликацию (`pendingDownloads` по ключу `room + url + duration`), чтобы два параллельных refill/prefetch не скачивали один и тот же URL дважды.

`read()`, `clearRoom()`, range-ответы и формат `/api/audio/:id` не меняются.

## 3. `server/audioDelivery.ts`

Прокинуть его в `cacheTrackAudio`:

audioUrl: await options.cacheTrackAudio(roomCode, track.audioUrl, {

`minPlayable` и батчирование по 4 (`server/audioDelivery.ts:22`) оставить без изменений. При желании можно уменьшить батч до 2, но после обрезки это не критично.

## 4. `server/index.ts`

### `start_game`

В `prepareRoomTrackAudio` передать длительность вопроса:

```ts
await prepareRoomTrackAudio(

```

Изменить `prepareRoomTrackAudio` (`server/index.ts:422-430`), чтобы она принимала `clipDurationMs` и передавала его в `prepareTrackAudio`.

### `hydrateRoomTrackPool`

Сейчас фоновая гидратация кэширует весь пул (`server/index.ts:454`). Как минимум передать `room.settings.questionDurationMs` в `prepareRoomTrackAudio`. Если оконная схема уже реализована — здесь кэшировать только метаданные и пополнять окно.

### Оконный prefetch

Если реализуется оконная схема, все вызовы `cacheTrackAudio` при `ensureAudioWindow()` / `refillAudioWindow()` должны получать `room.settings.questionDurationMs`. Настройки меняются только в лобби (`server/game.ts:195-197`), поэтому в рамках одной игры длительность стабильна.

### Очистка

Новых структур это дополнение не добавляет, но при очистке комнаты/окна нужно очищать и обрезанные записи через существующий `audioCache.clearRoom()`.

## 8. Риски и ограничения

- Прокси или upstream, который буферизует ответ целиком, не позволит прервать загрузку — сработает fallback «скачать и отбросить лишнее».
- MP3 с free-format или повреждёнными кадрами будет пропущен; это лучше, чем скачивать его целиком.
- Не-MP3 источники в `cache`-режиме не поддерживаются; demo-пул iTunes (`.m4a`) в этом режиме не даст playable-треков.
- Обрезка по кадрам не перекодирует звук: возможен резкий обрыв на 10/15/30 секунде, но файл остаётся валидным MP3.
- При длительности вопроса больше 10 секунд клип будет длиннее 10 секунд — это соответствует выбранному поведению «длительность вопроса, но не более 30 секунд».
- Дополнение не отменяет необходимость оконной схемы: обрезка уменьшает размер одного трека, а окно ограничивает их количество. Их лучше реализовывать вместе или сначала обрезку, затем окно.
